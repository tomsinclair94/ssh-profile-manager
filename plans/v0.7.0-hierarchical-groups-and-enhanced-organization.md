# SSH Profile Manager v0.7.0 - Implementation Plan

**Release Focus:** Enhanced Group Management, Hierarchical Organization, Export/Import Improvements, Favorites, Icons & Tags

---

## Overview

This release transforms SSH Profile Manager from a flat group structure to a hierarchical system with sub-groups, individual export/import, encrypted backups, and enhanced organization features (favorites, icons, tags).

**Key Changes:**
- Database migration from denormalized groups to normalized hierarchy
- Sub-group support with up to 3 nesting levels
- Individual profile/group export/import with append mode
- Encrypted exports with AES-256-GCM and HMAC integrity verification
- Favorites system for profiles and groups
- Icon picker for profiles
- Tag system with color-coding and filtering

## Database Schema Changes

### New Tables

**1. groups** - Normalized group hierarchy
```sql
CREATE TABLE groups (
    id TEXT PRIMARY KEY,              -- UUID
    name TEXT NOT NULL,               -- Unique within parent
    parent_id TEXT,                   -- NULL = top-level, references groups(id)
    path TEXT NOT NULL UNIQUE,        -- Full path: "Production/WebServers"
    icon TEXT,                        -- Icon identifier
    is_favorite BOOLEAN DEFAULT 0,
    display_order INTEGER DEFAULT 0,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY (parent_id) REFERENCES groups(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX idx_groups_unique_name_parent
    ON groups(name, COALESCE(parent_id, ''));
CREATE INDEX idx_groups_parent ON groups(parent_id);
CREATE INDEX idx_groups_path ON groups(path);
```

**2. profile_metadata** - Extended profile properties
```sql
CREATE TABLE profile_metadata (
    profile_id TEXT PRIMARY KEY,
    icon TEXT,
    is_favorite BOOLEAN DEFAULT 0,
    display_order INTEGER DEFAULT 0,
    FOREIGN KEY (profile_id) REFERENCES profiles(id) ON DELETE CASCADE
);
```

**3. tags** - Shared tag definitions
```sql
CREATE TABLE tags (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    color TEXT NOT NULL,              -- Hex color (#RRGGBB)
    created_at TEXT NOT NULL
);
```

**4. profile_tags / group_tags** - Many-to-many tag assignments
```sql
CREATE TABLE profile_tags (
    profile_id TEXT NOT NULL,
    tag_id TEXT NOT NULL,
    PRIMARY KEY (profile_id, tag_id),
    FOREIGN KEY (profile_id) REFERENCES profiles(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE
);

CREATE TABLE group_tags (
    group_id TEXT NOT NULL,
    tag_id TEXT NOT NULL,
    PRIMARY KEY (group_id, tag_id),
    FOREIGN KEY (group_id) REFERENCES groups(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id) REFERENCES tags(id) ON DELETE CASCADE
);
```

### Modified Tables

**profiles** - Add foreign key to groups
```sql
ALTER TABLE profiles ADD COLUMN group_id TEXT REFERENCES groups(id) ON DELETE RESTRICT;
CREATE INDEX idx_profiles_group ON profiles(group_id);
-- Keep group_name temporarily for migration, drop in v0.8.0
```

### Migration Strategy (Version 4)

1. Create all new tables
2. Extract unique group names from `profiles.group_name`
3. Create group records with paths (handle nulls as "Ungrouped")
4. Populate `profiles.group_id` by matching paths
5. Validate all profiles have valid group_id
6. Keep `group_name` column until v0.8.0 for rollback safety

### Encryption Implementation

**Dependencies (add to Cargo.toml):**
```toml
aes-gcm = "0.10"
pbkdf2 = { version = "0.12", features = ["simple"] }
rand = "0.8"
base64 = "0.21"
sha2 = "0.10"
hmac = "0.12"
```

**Approach:**
- **Encryption**: AES-256-GCM (authenticated encryption)
- **Key Derivation**: PBKDF2-HMAC-SHA256 with 600,000 iterations
- **HMAC**: Additional HMAC-SHA256 over ciphertext for integrity
- **Random Values**: 16-byte salt, 12-byte IV per export
- **Password Validation**: Min 12 chars, complexity check
- **Security**: Mandatory encryption when passwords included

**Flow:**
1. User password → PBKDF2 (600k iterations, random salt) → 256-bit key
2. Export data → JSON serialize → AES-256-GCM encrypt (random IV) → Base64
3. HMAC-SHA256 over ciphertext
4. Return EncryptedExport struct

**Import verification:**
1. Parse EncryptedExport
2. Derive key from password + stored salt
3. Verify HMAC (fail fast if tampered)
4. Decrypt ciphertext
5. Deserialize JSON and import

## Critical Implementation Details

### 1. Group Path Management

**Format:** `"ParentGroup/SubGroup/DeepGroup"` (forward slash delimiter)

**Path calculation:**
- On create: Concatenate parent.path + "/" + name
- On rename: Update group path + recursively update all descendant paths
- On move: Recalculate path based on new parent

**Depth limit:** Maximum 3 levels (top-level + 2 sub-levels)

**Validation:**
- Prevent circular references (database FK constraints)
- Prevent moving group into its own descendant
- Validate depth on create/move

### 2. Profile Uniqueness Rules

**Current:** Profile names globally unique

**v0.7.0:** Profile names unique within parent group only

**Validation:**
```rust
fn validate_profile_name_in_group(
    db: &Database,
    name: &str,
    group_id: &str,
    exclude_id: Option<&str>
) -> Result<(), String>
```

Allows: "Production" profile in both "AWS/WebServers" and "Azure/WebServers" groups

### 3. Group Deletion Modes

**Two options presented to user:**

1. **Delete All (Cascade):**
   - Delete group, all sub-groups, all profiles
   - Destructive, requires confirmation

2. **Move Profiles to Parent:**
   - Delete group and sub-groups
   - Move all profiles to parent group (or "Ungrouped" if top-level)
   - Preserves profiles

**Confirmation dialog:**
```
This group contains 15 profile(s) and 3 subgroup(s).

[Delete All] [Move Profiles to Parent] [Cancel]
```

### 4. Export/Import Modes

**Two distinct modes:**

**A. Individual Export/Import (Append Mode)** - Phase 4
- Export: Single profile or single group (with all sub-groups and profiles)
- Import: Checks for duplicates, prompts user:
  - Duplicate detection: name + group_id (allows same name in different groups)
  - Profile options: Skip / Rename (auto-suffix) / Overwrite
  - Group options: Skip / Rename (auto-suffix) / Merge
  - Applied per conflict
- Connection details (host, username) NOT part of duplicate detection

**B. Full Backup/Restore (Replace Mode)**
- Export: All profiles, all groups, all settings
- Import: Delete all existing data, import as complete replacement
- Confirmation: "This will replace all existing data. Continue?"

**Settings Export/Import:**
- Rename UI labels to "Backup Settings" / "Restore Settings"
- Behavior unchanged: full replacement

**Version Tracking:**
- Need to discuss this in more depth before identifying how to do this
- Export/Import of any of the profile methods should track conflicts
- If any major changes are made to profile handling that prevents an import, this should be tracked
- Export always contains the version it was exported in
- Import need to ensure that the version is possible to import without breaking (if it's not, user cannot import those profiles)

### 5. Encryption Mandatory Conditions

**Encryption REQUIRED when:**
- Export includes any profiles with password auth method
- User cannot opt-out

**Encryption OPTIONAL when:**
- Export contains only key-based or no-auth profiles
- User can choose encrypted or plaintext

**Password strength:**
- Minimum 12 characters
- Recommend: mix of upper, lower, numbers, symbols
- Frontend shows strength meter

## Trade-offs & Decisions

### 1. Group Storage: Normalized vs. Path-Only
**Chosen:** Normalized with calculated path field

**Pros:** Referential integrity, easy renames, cascade deletes, proper SQL
**Cons:** More complex queries, path calculation overhead

**Justification:** Data integrity and maintainability outweigh query complexity.

### 2. Profile Name Uniqueness: Global vs. Per-Group
**Chosen:** Unique within parent group only

**Pros:** More flexible, natural organization, filesystem-like
**Cons:** Duplicate detection more complex, can't reference by name alone

**Justification:** User requirement, improved UX, manageable complexity.

### 3. Export Encryption: Optional vs. Mandatory
**Chosen:** Mandatory when passwords included, optional otherwise

**Pros:** Enforces security for sensitive data, flexibility for non-password exports
**Cons:** Extra step for users

**Justification:** Security best practice, clear security posture.

### 4. Depth Limit: 3 Levels
**Chosen:** 3 levels (top + 2 sub-levels)

**Pros:** Cleaner UI without visual cramping, sufficient for most organizational needs
**Cons:** Less flexibility for very complex structures

**Justification:** Simpler and cleaner without risking UI complexity, adequate for typical use cases.

### 5. Icon Set: Custom Upload vs. Predefined
**Chosen:** Predefined icon library (Font Awesome or similar)

**Pros:** Consistent style, no file management, immediate availability
**Cons:** Limited choices

**Justification:** Simpler implementation, professional appearance, sufficient variety.

## Security Considerations

### Encryption
- **Algorithm:** AES-256-GCM (authenticated encryption)
- **Key Derivation:** PBKDF2-HMAC-SHA256, 600k iterations (OWASP 2023)
- **HMAC:** SHA256 over ciphertext (separate verification)
- **Random Values:** Cryptographically secure RNG for salt/IV
- **Password Strength:** Min 12 chars, complexity validation
- **Memory Safety:** Zeroize passwords/keys after use

### Input Validation
- **Group Names:** Alphanumeric, spaces, limited special chars, max 64 chars
- **Path Injection:** Validate '/' delimiter usage, prevent path traversal
- **Depth Limit:** Max 3 levels (prevent stack overflow)
- **Circular References:** Database FK constraints
- **Tag Names:** Alphanumeric + spaces, max 32 chars
- **Color Codes:** Validate hex format (#RRGGBB)

### SQL Injection Prevention
- Parameterized queries (existing pattern)
- UUID validation before queries
- Rusqlite prepared statements exclusively
