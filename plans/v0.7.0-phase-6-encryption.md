## Overview

Phase 6 implements robust encryption for export/import functionality using industry-standard cryptography. All exports containing profiles with password authentication are mandatorily encrypted to protect sensitive credentials.

**Key Features:**
- AES-256-GCM authenticated encryption
- PBKDF2-HMAC-SHA256 key derivation (600k iterations - OWASP 2023)
- Additional HMAC-SHA256 integrity verification (fail-fast)
- Password strength meter with visual feedback — 5-level scale: Weak / Fair / Good / Strong / Stronger (non-enforcing)
- Mandatory encryption when password-based profiles are included
- Progress indicators for encryption/decryption operations

## Architecture Overview

### Encryption Flow
```
User Password (12+ chars)
    ↓
PBKDF2-HMAC-SHA256 (600k iterations, random 16-byte salt)
    ↓
256-bit Encryption Key
    ↓
Export Data → JSON serialize → AES-256-GCM encrypt (random 12-byte IV)
    ↓
Ciphertext + Auth Tag
    ↓
HMAC-SHA256 over (salt + IV + ciphertext)
    ↓
Base64 encode all components
    ↓
EncryptedExport struct
```

### Decryption Flow
```
EncryptedExport
    ↓
Parse and decode Base64 components
    ↓
Verify HMAC-SHA256 (fail fast if tampered)
    ↓
PBKDF2-HMAC-SHA256 (user password + stored salt)
    ↓
AES-256-GCM decrypt (verify auth tag)
    ↓
JSON deserialize
    ↓
Import data structures
```

### Data Structure

```rust
struct EncryptedExport {
    version: String,          // Export format version (e.g., "2.0")
    encrypted: bool,          // Always true for encrypted exports
    cipher: String,           // "AES-256-GCM"
    kdf: String,              // "PBKDF2-HMAC-SHA256"
    kdf_iterations: u32,      // 600000
    salt: String,             // Base64-encoded 16-byte salt
    iv: String,               // Base64-encoded 12-byte IV (nonce)
    data: String,             // Base64-encoded ciphertext
    hmac: String,             // Base64-encoded HMAC-SHA256
}
```

#### Fixes Applied (2026-02-05)

The following issues were identified and fixed during Phase 6E testing:

**Encryption Modal UI:**
- Help text restructured: "If you forget this password..." moved onto its own line; "Recommended: 16+ characters..." moved into a hover tooltip on the password input field (same `.input-tooltip` pattern used on Profile Name, Group Name, etc. — auto-hides while typing)
- Character counter added to both password and confirm password fields (`0 / 128`), matching the existing counter pattern across the app
- 128-character upper limit added — enforced in both frontend validation and backend `validate_encryption_password`

**Password Strength Meter:**
- Bar colours were driven by width classes (`strength-width-25`, etc.) which had hardcoded colours shifted one step from the label colours (e.g. the bar at 25% was red but the label at score 1 was orange). Decoupled: width classes now set only `width`; colour is set by the strength classes (`strength-weak` / `strength-fair` / `strength-good` / `strength-strong` / `strength-stronger`), matching the labels exactly
- Width mapping changed from `[0, 25, 50, 75, 100]` to `[20, 40, 60, 80, 100]` — the old mapping had Weak at 0% (invisible bar) and scores 3 and 4 both labelled "Strong" but at different widths (75% vs 100%)
- Added 5th distinct level "Stronger" (score 4, dark green `#16a34a`) replacing the collapsed Strong/Strong display. Full scale: Weak (20%, red) → Fair (40%, orange) → Good (60%, yellow) → Strong (80%, green) → Stronger (100%, dark green). Score breakdown: length contributes 0–2 points (+1 at ≥12 chars, +1 at ≥16 chars), character variety contributes 0–2 points (+1 for 3 of 4 classes, +1 for all 4)

**Backend Password Validation (`validate_encryption_password`):**
- `.len()` → `.chars().count()`: the min-length check previously counted UTF-8 bytes, not characters. A 6-character Cyrillic password (`"пароль"` = 12 bytes) would have passed the 12-character minimum. Now counts characters, matching the frontend
- 128-character max added, matching frontend enforcement
- 4 new unit tests: 128-char boundary and 129-char over-limit, both ASCII and multibyte Unicode. Existing test comments updated to reflect character-based counting

## Security Considerations

### Cryptographic Choices

**Why AES-256-GCM?**
- Industry standard for authenticated encryption
- Single primitive for confidentiality + integrity
- Hardware acceleration on modern CPUs
- Recommended by NIST, OWASP

**Why PBKDF2 with 600k iterations?**
- OWASP 2023 recommendation
- Sufficient resistance to brute-force attacks
- ~1-2 seconds on modern hardware (acceptable UX with spinner)

**Why additional HMAC-SHA256?**
- Defense-in-depth: AES-GCM auth tag + separate HMAC
- Fail-fast verification before decryption attempt
- Prevents certain cryptographic attacks on GCM

### Threat Model

**Protected Against:**
- Brute-force password attacks (600k iterations + strong password recommendation)
- Data tampering (HMAC verification + GCM auth tag)
- Chosen-ciphertext attacks (authenticated encryption)
- Timing attacks (constant-time HMAC comparison)
- Password leakage (zeroization after use)

**NOT Protected Against:**
- Weak user passwords (users can ignore strength meter)
- Keyloggers/screen capture (out of scope)
- Compromised devices (OS-level threat)

### Best Practices Implemented

1. **Random Salt/IV** - Generated per export (prevents rainbow tables, replay attacks)
2. **Zeroization** - Passwords/keys cleared from memory immediately after use
3. **Fail-Fast** - HMAC verified before attempting decryption
4. **Constant-Time Comparison** - HMAC verification prevents timing attacks
5. **Version Tracking** - Export format includes crypto parameters for future-proofing
6. **Strong Defaults** - 600k iterations, 256-bit keys, 12-byte IVs (OWASP/NIST compliant)

## Error Handling Reference

### Export Errors

| Error | User-Facing Message |
|-------|---------------------|
| Missing encryption password | "Encryption required: This export contains password-authenticated profiles. Please provide an encryption password." |
| Password too short | "Password must be at least 12 characters." |
| Password too long | "Password must not exceed 128 characters." |
| Passwords don't match | "Passwords do not match. Please re-enter." |
| Encryption failure | "Encryption failed: [detail]. Please try again." |

### Import Errors

| Error | User-Facing Message |
|-------|---------------------|
| No password provided | "This import is encrypted. Please provide the decryption password." |
| Wrong password | "Incorrect password. Please try again." |
| HMAC mismatch | "Import file is corrupted or has been tampered with. Cannot import." |
| Corrupted data | "Import file is corrupted or invalid. Cannot import." |

## Known Limitations (Acceptable for v0.7.0)

- **No password recovery:** If user forgets encryption password, data is unrecoverable (by design)
- **No password complexity enforcement:** Users can choose weak passwords (strength meter guides but doesn't block)
- **Single encryption method:** AES-256-GCM only, no cipher selection
- **No key rotation:** Re-encryption requires full decrypt → re-encrypt cycle
- **Decrypt modal button spinner (WKWebView):** The loading spinner on the Import button translates across the button instead of rotating in place. WKWebView does not correctly resolve `position: absolute` + `transform` centering inside `<button>` elements. Needs alternative layout approach — see Phase 6E Spinners & Feedback for details. Cosmetic only; the loading state (disabled inputs/buttons, colour change) still works.

**Future Considerations (v0.8.0+):**
- Encrypted local database (not just exports)
- Cloud backup with end-to-end encryption
- Hardware security module integration
